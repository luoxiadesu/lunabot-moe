# LunaBot performance investigation — 2026-10-01

The production bot on 47.91.23.232 was sampled without restarting or injecting
commands. No messages were sent by the investigation. Built-in timing was enabled
for 120 seconds and restored. py-spy 0.4.2 was installed into the separate temporary
directory `/tmp/lunabot-perf-tools`, leaving the bot virtual environment unchanged.

## Findings in plain language

1. Plain group messages incur a substantial amount of command-dispatch overhead,
   even when they are not commands. This is the best target for reducing routine
   main-process CPU usage. Do not simply discard all plain messages: logging,
   water statistics, automatic chat and other message-driven features need them.
2. Decorative triangle backgrounds repeatedly resize 2048×2048 images into tiny
   triangles. Preparing smaller source images and caching them in drawing workers
   should substantially reduce this particular cost without removing backgrounds.
3. Memory is mostly loaded game data and drawing-worker state. Measurements do
   not establish a leak. Reduce duplicated/deep-copied master data and bound image
   caches before reducing drawing concurrency, which trades memory for latency.
4. Korean recommendation updates fail repeatedly because track 707 has missing
   `event_rate` values. This is a correctness/retry problem, not the main CPU cost.

of all server CPU. Nonblocking py-spy intentionally does not pause the process;
sample errors and workload variation limit precision. Inclusive frames overlap
and must not be added together. The sample included real image rendering, but
is not a complete representation of every command or peak event.

## Reproducible checks

### Command dispatch

A separate Python process on the server initialized NoneBot 2.4.4 with 0, 50,
150 and 250 dummy command matchers. It processed 20 plain messages after warm-up,
without plugins, a real bot connection, or outgoing API calls:

| Dummy matchers | CPU milliseconds per plain message |
|---:|---:|
| 0 | 0.089 |
| 50 | 25.099 |
| 150 | 84.212 |
| 250 | 143.252 |

Static source inspection found 257 command/message/notice registration calls
across the bot source; this is not an exact runtime matcher count. Framework
inspection confirms every priority's matchers are dispatched through task groups
and each rule uses another task group. The synthetic benchmark demonstrates
scaling behavior and should not be presented as production command latency.

Suggested change: dispatch known command handlers through a command-indexed
entry point, while preserving non-command plugins, temporary conversation
matchers, aliases, priority and blocking semantics. This needs focused regression
tests; avoid directly replacing NoneBot internals based only on this sample.

### Triangle images

The active blue background uses three 2048×2048 RGBA PNGs. In a separate process,
100 seeded target sizes between 32 and 200 pixels were resized with BILINEAR:

| Source | Median CPU time, three runs |
|---|---:|
| Original 2048 px image | 2.9783 s |
| Image prepared once at 256 px | 0.0682 s |

This is about 43.7× for the resize sub-operation, not a 43.7× speedup of complete
rendering. It excludes the one-time preparation and uses small target sizes.
A production solution should use cached source levels (e.g. 128/256/512/1024),
select a level at least as large as the target and retain originals for large
triangles. Cache by path + file version with a memory bound. Compare output with
fixed random seeds before rollout; do not repeatedly downscale an already small
image or force every target through 256 px.

Gradient construction also creates full-size coordinate arrays and float64
intermediates; broadcasting/float32 and cached size-independent color assets
are additional candidates after the triangle change.

### Master-data memory

Startup logs show 69 loaded region/table pairs with about 203 MiB of raw JSON.
Largest include JP costume3ds (54.4 MiB), gachas (47.2 MiB), cards (33.8 MiB),
and virtualLives (14.6 MiB). Python objects and indexes are larger than their raw
JSON representation. Some startup logs predate the sampled memory snapshot, so
this is an explanation of likely footprint rather than exact heap attribution.

The deck updater calls `get_path()`, which also loads and indexes a table in the
bot before the separate recommendation service reads it. Investigate a file-only
cache freshness path for updates that do not need Python objects. Image caches in
`RegionRipAssetManger` have no global byte/count bound. A longer memory growth
study or controlled allocation profiling is needed before claiming leakage.

Four drawing processes are configured. Cutting to two can reduce resident memory
but may increase busy-hour queues; do not change that solely to make idle RSS
smaller. Linux swap usage alone does not mean the bot is currently thrashing.

### Korean recommendation failure

30-minute logs contained 60 identical `float += NoneType` errors. Using only the
pure averaging function and the cached MusicMeta files reproduced the failure
in about 5.2 ms. KR track 707 hard/expert/master has `event_rate=null`; existing
JP fallback fills only `music_time` and leaves these values unresolved.

Recommended fix: validate metadata before averaging and exclude incomplete
entries from the synthetic random-song average, reporting skipped entries once
per source version. Do not silently replace missing scoring values with zero.
Add per-region/version backoff so unchanging invalid data is not retried every
30 seconds. Validate the consumer's treatment of incomplete original entries
before deploying a scoring-data change.

## Other confirmed code risks

- `ExpirableCache.get` sweeps the entire cache on every lookup; move expiration
  cleanup to an occasional sweep or bounded LRU/TTL cache if profiles show growth.
- Font cache entries' `last_used` values are set on insertion but not on cache
  hits, so intended LRU eviction actually behaves like insertion-age eviction.
- `WebJsonRes` does not advance a retry timestamp after a failed update, allowing
  concurrent readers to retry an unhealthy upstream repeatedly; coalesce refreshes
  and add failure backoff.
- Generic interval scheduling catches up missed ticks immediately after a long
  task. MySekai now uses fixed-delay reconciliation, but other jobs still use the
  generic scheduler. Choose skip-missed behavior explicitly per job.

These are inspected code properties; their production cost was not individually
measured. Prioritize command dispatch and background rendering based on samples.

## Subsequent fixes

The later Haruki engine migration implemented scoring metadata validation,
per-region failure backoff and removal of unchanged metadata DB writes; see
[deployment notes](../operations/haruki-deck-20261001.md). The command-dispatch,
triangle rendering and memory recommendations above remain recommendations,
not deployed optimizations. Temporary profiling tools/copies were subsequently
cleaned; retained server evidence is described in the command audit report.
